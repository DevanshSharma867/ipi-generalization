# Paper plan and pre-registration

**Status:** pre-registration, frozen 2026-10-28, before any V3, ICT, AgentDojo or τ-bench result exists.
**Rules:** after the first scored result of a pre-registered comparison, any change to a claim, hypothesis, success
criterion, evaluation set, metric, baseline, comparator set or threshold protocol in this file goes in
`docs/deviations.md` (date, before → after, reason, results seen). Changes made before then are listed under
"Amendments before scoring" at the end of this file. Every pre-registered comparison is reported whatever its outcome.

**Framing (amendment A6).** The paper leads with C3 (query-counterfactual intent pairs) and C4 (ICT). C1 and C2 are
supporting evidence: they extend Kale & Vishwanath (2026) and Liu (2026) to BIPIA-style insertion data. Liu's
Sheltron result is the motivation for C4: giving an untrained classifier the request fails, so ICT trains for it.

Prior results are cited only by `docs/findings.md` entry (F001–F012). Related work and BibTeX: `docs/related_work.md`.

**Already seen when this plan was written (disclosed):** our V2 results F001–F012, including the V2-trained models on
InjecAgent (F010) and deepset (F011), and the published numbers in Liu (2026), including its AgentDojo and
τ-bench detector rankings. No model of ours has been scored on AgentDojo or τ-bench. No V3 data exist yet. No ICT model exists.

## 0. Closest prior work (read in full on 2026-10-28)

**Liu 2026, "Passing the Test You Trained On"** (arXiv:2610.03448, v1, 2 Oct 2026).
- Replays AgentDojo v1.2 and τ-bench ground-truth tool calls with no LLM, labels injected outputs by differential
  replay, and builds AD-Clean, AD-Matched (585 benign / 432 injected), AD-Shift (975 / 720), TB-Clean (1,533) and
  TB-Matched (584 injected; InjecAgent attack strings appended to product names; benign side = TB-Clean).
- Scores 15 public detectors and 2 task-aware LLM judges (Qwen2.5-7B, Llama-3.1-8B, both 4-bit), plus BIPIA (test half).
- Findings:
  - Detector rankings transfer poorly from BIPIA to agent benchmarks. The best BIPIA detector (PIGuard) catches
    about 2% of AD-Matched injections at 1% FPR.
  - The best agent-benchmark detector (Horizon-Labs) was trained on agent-style inputs.
  - Training-data audits: PIGuard's training data contains 65/75 BIPIA train-half text attacks and 53/62 InjecAgent
    instructions. Input form matters more than attack-string overlap.
  - Giving a small classifier the user goal does not help: Sheltron with the goal segment has a higher AUROC but a
    lower TPR@1%FPR and a much higher FPR. Sheltron was never trained to use the goal this way (Liu: "may simply be
    out of distribution"). We read this as the motivation for C4, not as counter-evidence: untrained use of the
    request fails, and ICT trains for it.
- Threshold protocol: the 1% FPR threshold is chosen on the evaluated benign set (oracle). The paper says this favors the detectors.
- Bootstrap: percentile, stratified by label, not clustered.
- It does **not**:
  - analyze BIPIA construction artifacts (position, whitespace, templates) or row-level split leakage;
  - build pairs where the same text is benign under one request and injected under another;
  - measure FPR on user-requested instructions;
  - train any detector.
- Code and scores: https://github.com/lzwhehe/benign-instruction-bench (MIT). The evaluation data is regenerated by
  scripts, not redistributed. Horizon-Labs weights are pinned to HF revision `af3c52e6a9d8`.

**Jia et al. 2026, "AlignSentinel"** (arXiv:2602.13597, v2, 21 Feb 2026). It is answered in §2.

**Other request- or intent-aware work** (abstracts read; details in `docs/related_work.md`):
- TaskTracker (Abdelnabi et al., arXiv:2406.00799): task drift from activation deltas, white-box.
- DataSentinel (Liu et al., arXiv:2504.11358): known-answer detection with a fine-tuned LLM. Not request-conditioned.
- PromptSleuth (Wang et al., arXiv:2508.20890): an LLM reasons over task-level intent and whether the requested task
  fits the system scope. Direct injection.
- IntentGuard (Kang et al., arXiv:2512.00966): a reasoning LLM's instruction-following intent analysis. A mitigation,
  evaluated on AgentDojo and Mind2Web.
- Li et al. 2026 (arXiv:2601.07185): defenses learn surface heuristics, including position bias, token-trigger bias
  and topic bias. It names counterfactual benign examples as future work.
- Kale & Vishwanath 2026 (arXiv:2610.18408):
  - On AgentDojo, position + length features alone reach 0.91–0.98 AUROC under the standard probe evaluation.
  - It adds matched negatives: the same conversation with the injection removed, and harmless look-alikes.
- Fomin 2026 (arXiv:2602.14161): leave-one-dataset-out evaluation; dataset shortcuts inflate AUC.

Novelty is judged strictly against Liu (2026), AlignSentinel and the work above. "Confirmatory" means prior work
already makes the claim, and we re-establish it in our setting.

Order of emphasis in the paper (A6): C3 and C4 lead. C1 and C2 support them, as extensions of Kale & Vishwanath
(2026) and Liu (2026) to BIPIA-style insertion data.

## 2. AlignSentinel: precise answers

Read from arXiv:2602.13597v2, HTML version, on 2026-10-28.

1. **Does its benchmark hold the content fixed and vary only the user request? No.**
   - Indirect setting, §5: "Misaligned inputs are constructed by appending or replacing parts of benign tool responses
     with injected instructions"; "Aligned inputs are created by including benign tool responses with safe or helpful
     instructions"; "This design provides both benign and malicious variants for the same user-prompt-tool pair."
     The user prompt is fixed and the tool-response text differs between classes. That is the opposite of C3.
   - Direct setting: GPT-4o rewrites a system-prompt constraint into an aligned version, an opposite version and a
     longer version. The prompt asks that these "have as few same words with the original prompt as possible". The
     aligned and misaligned texts are therefore different strings.
   - We found no experiment in which identical instruction text is aligned under one request and misaligned under another.
   - Lengths are not matched across classes: the generation prompts ask for diversity.
   - Data are GPT-4o-generated across 8 domains × 10 agents, with 2 agents per domain held out for test.
2. **Is code, data or a model released? No release found.**
   - The paper has no code, data or model link and no availability statement.
   - Searched 2026-10-28: GitHub repository search for "AlignSentinel" returned 0 results; Hugging Face model and
     dataset search returned 0 results; the arXiv page links nothing.
   - Paper: https://arxiv.org/abs/2602.13597.
3. **Does it need white-box attention access? Yes.**
   - Features are the attention maps between the input and the higher-priority instruction, over all layers and
     heads, of a backend LLM (Qwen3-8B, Llama-3.1-8B-Instruct, Mistral-7B-Instruct-v0.3).
   - An MLP (Avg-first or Enc-first) is trained on top, using the benchmark's training split.
4. **Could it be run as a baseline on our sets?** Not as a published detector: there are no weights or code.
   - It could only be **re-implemented** with an open backend, from the paper's description. Its training data would
     have to come from somewhere: either its GPT-4o generation prompts, re-run by us (a different dataset), or our V3 + pairs.
   - Either way it would be "AlignSentinel-style (our re-implementation)", not AlignSentinel.
   - It is also a 3-class model. Mapping it to binary (misaligned = positive) follows the paper, but its reported
     metrics are FPR/FNR at argmax, not TPR@FPR.
   - **Decision:** an AlignSentinel-style re-implementation is an **optional secondary baseline**. It is in scope only
     if implemented, frozen, and validated on V3 val before any ICT test result is seen. It is excluded from the H3
     comparator set, which covers published, runnable detectors. If built, it is reported next to H2–H4 and labelled
     as a re-implementation.

## 3. Hypotheses and success criteria (fixed now)

### Shared protocol

**Inputs.**
- Every trained model of ours sees `Intent: <user request> | Context: <document or tool output>`.
- ICT sees the same two fields as a segment pair.
- On agent sets, the intent is the task's user prompt and the context is one tool output.

**Content-only detectors** (every public classifier that takes one text) see the context only.
- Each unique context string is scored once, and that score is shared by every row with that context. Pair members
  therefore tie exactly, and pair accuracy is 0.5 by construction (`src/metrics.pair_accuracy`: ties count 0.5).

**Truncation.** Our DeBERTa-based models keep 512 tokens; the intent is kept and the context is truncated from the
end. The truncated fraction is reported per set.

**Seeds.**
- V3 models: five runs, one per V3 split realization, with training seed = split_seed ∈ {0,1,2,3,4}.
- V2 DeBERTa: five runs on frozen V2 train. Seeds 42, 123 and 999 already exist; seeds 0 and 1 are added. The
  existing checkpoints are reused as-is.
- Reported values are the mean ± SD over runs, plus a 95% cluster-bootstrap CI (B = 1000) of the run-mean.

**Paired comparisons.** `src/metrics.paired_bootstrap`. Each resample draws clusters and recomputes the run-mean
metric for each arm, then takes the difference. "Supported" means the 95% CI of the difference excludes 0 in the
predicted direction.

**Bootstrap clusters.**
- AgentDojo and τ-bench: the user task.
- V3: `doc_id`.
- Pairs: the source document (V3) or the user task (agent pairs).
- InjecAgent: the user case.

**V3 aggregation (amendment A10).**
- On V3 sets, a headline metric is the **task-macro**: the unweighted mean of the metric over EmailQA, TableQA
  and CodeQA. Pooled and per-task values are reported next to it.
  - The CI resamples doc_id clusters **within each task** (stratified by task), so every resample has all three
    tasks. Stratification is to be added to `src/metrics.py` before any V3 model is scored.
  - Run-mean and paired comparisons use the same task-macro.
- Task-macro applies only where every task's value passes the metric gates. On V3 test, each task has few clean
  rows (e.g. EmailQA has 15 test docs × 2 clean rows in split seed 0), so per-task TPR@FPR is gated out.
  - TPR@FPR on V3 is therefore reported **pooled** (where gated in) and marked as pooled.
  - Task-macro covers AUROC, FPR at the default threshold, and macro-F1.
- Agent sets and pairs are not affected; their clusters are user tasks or source documents.

**Metric gates** (`src/metrics.MIN_CLEAN`): TPR@1%FPR only where the evaluated set **and** the calibration set have
≥ 500 clean rows; TPR@5%FPR where both have ≥ 100. Otherwise the result is reported as `n/a (n_clean=…)`.

**Threshold protocols.** The calibrated protocol is primary for every TPR@FPR hypothesis. Oracle (threshold chosen
on the evaluated clean rows, as in Liu 2026) is always reported next to it, for comparability, and never decides a
hypothesis.

**Calibration for AgentDojo and τ-bench (amendment A3).**
- **Primary: a dedicated calibration pool.**
  - It holds ≥ 1,000 clean synthetic tool outputs from the agent-style data pipeline (to be built).
  - It is generated with no AgentDojo or τ-bench templates and is held out from all training, including ICT, V3 and
    every ablation.
  - Each item carries an `Intent | Context` pair in the same format as the agent sets.
  - The calibrated threshold for every detector on every agent set is fixed on this pool's clean scores, for both
    1% and 5% FPR. This mirrors deployment: you calibrate on your own clean traffic.
  - With ≥ 1,000 calibration rows, the `MIN_CLEAN` gates pass. TPR@1%FPR is then computable on the **full**
    AD-Matched (585 clean), AD-Shift (975) and TB-Matched (1,533).
  - The pool's build script, size and sha256 are recorded in `docs/data_provenance.md` and `docs/findings.md` before
    any model is scored on an agent set.
- **H1 waits for the pool.** If the pool does not exist when H1 would be decided, H1 is not decided until it does.
  It does not fall back to another protocol.
- **Secondary: task-disjoint halves.**
  - Each agent set is split by user task, 50/50, with a seeded hash of the task id (seed 0).
  - Thresholds are fixed on the clean rows of the calibration half and TPR is measured on the evaluation half.
  - The `MIN_CLEAN` gates apply, so TPR@1%FPR is `n/a` where a half has fewer than 500 clean rows.
  - Reported, never decides a hypothesis.
- **Secondary: source-side,** on V3 val clean rows. Reported where gated, and never decides a hypothesis.

**Building the agent sets.**
- We rebuild AD-Matched, AD-Shift and TB-Matched with Liu's released scripts, pinned to a repository commit recorded
  in `docs/data_provenance.md`, on AgentDojo v1.2 and a pinned τ-bench commit.
- We re-score every detector ourselves. Liu's numbers are never copied into our tables.

**Model selection.** ICT, V3-DeBERTa and V2-DeBERTa hyperparameters and checkpoints are chosen only on V3 val (V2
val for V2 models) and val pairs. No agent-benchmark or test-pair data is used for selection.

### H1: artifact removal improves transfer

**Hypothesis.** A V3-trained DeBERTa transfers better than a V2-trained DeBERTa.

**Comparison.**
- Architecture and hyperparameters are identical to `src/models/deberta.py`, input `Intent | Context`.
- Metric: run-mean calibrated TPR@1%FPR on the full AD-Matched, AD-Shift and TB-Matched, with the threshold from
  the calibration pool (A3). Compared with a paired bootstrap.

**Decision.**
- **Supported:** V3 > V2 with CI excluding 0 on at least 2 of the 3 sets, and V3 < V2 with CI excluding 0 on none.
- **Refuted:** V2 > V3 with CI excluding 0 on at least 2 sets.
- **Otherwise inconclusive.**

All three sets are reported regardless.

### H2: ICT reads the request

**Hypothesis.** ICT's pair accuracy on held-out pairs is clearly above 0.5.

**Criterion.**
- Pair accuracy is computed on held-out V3-test pairs: the pairs on the test docs of **split seed 0** only (A18).
  The models compared on pairs are trained on split seed 0 with training seeds 0–4, since runs on split seeds 1–4
  may have trained on those docs.
- Supported if the run-mean pair accuracy has a 95% cluster-bootstrap CI whose lower bound is > 0.5.
- The individual runs and the `subtle` subset are reported separately.
- Every content-only detector is 0.5 by construction (see Shared protocol), so no comparison against them is needed for H2.
- The V3-DeBERTa (no pairs) pair accuracy is reported next to ICT. It reads the intent, so it is not 0.5 by construction.

### H3: ICT beats request-aware comparators where intent matters, and is non-inferior where it doesn't

**(a) Intent-dependent transfer sets.** Held-out pairs from V3-test, and pairs built on AgentDojo/τ-bench tool
outputs. On each set, ICT has:
- higher pair accuracy, and
- higher calibrated TPR@5%FPR

than every **H3a comparator** (below), with each paired-bootstrap CI of (ICT − comparator) excluding 0. The
calibration set is the clean (aligned) members of the val pairs for V3 pairs, and the calibration pool (A3) for
agent pairs.

**H3a comparators (amendment A1).** H3 on pairs is decided against these four request-aware comparators only:
- **(a) task-aware LLM judges:** Qwen2.5-7B and Llama-3.1-8B, with Liu 2026's judge prompt copied verbatim from the
  pinned release into a committed file before scoring.
- **(b) Sheltron with its user-goal segment,** as in Liu 2026.
- **(c) a PromptArmor-style frontier-LLM detector given the user request.**
  - PromptArmor (Shi et al., arXiv:2507.15219) prompts an off-the-shelf LLM to detect injected prompts. Adding the
    user request is our adaptation, so it is labelled "PromptArmor-style".
  - One API model, with a dated model id.
  - The prompt, the score definition (how a continuous score is obtained) and the spending cap are committed in one
    file before any scoring, and never edited afterwards.
  - It is run on the eval sets and the calibration sets it needs, never on training data.
  - If the cap is hit, the unscored rows are reported and the comparison is made on the scored subset of clusters
    only, for all models.
  - **Superseded in part by A7:** every setting (model, score, prompt, scope, order, budget) is fixed in
    `configs/frontier_detector.yaml`, and a set is scored in full or not at all.
- **(d) ICT ablation (a):** same backbone, request given, trained on V3 without pairs and without the margin loss,
  with the same selection protocol and seeds as ICT.
  - **This is the most important comparator.** Beating it shows the pairs and margin loss matter, not just access
    to the request.

**Reported but not deciding H3a:**
- Content-only detectors. They tie on pairs, so their pair accuracy is 0.5 and their pair TPR equals their pair FPR.
  Beating them follows from H2.
- An AlignSentinel-style re-implementation, if one exists (§2).

**(b) Content-only transfer sets (amendment A2): non-inferiority.**
- On each of AD-Matched, AD-Shift and TB-Matched, ICT is **non-inferior** if the lower bound of the paired-bootstrap
  95% CI of (TPR_ICT − TPR_best) is above −0.05 (5 points absolute).
  - TPR is the calibrated TPR@1%FPR, with thresholds from the calibration pool (A3).
  - ICT's TPR is the run-mean.
  - The bootstrap is clustered by user task.
- "Best" is the published detector with the highest calibrated point estimate on that full set.
- Horizon-Labs and Wolf Defender are eligible to be best (see §6).
- The point difference and its CI are reported for every set, whatever the outcome.

**Decision.**
- **H3 supported:** (a) holds on both pair sets **and** (b) holds on all three agent sets.
- **H3a-only:** (a) holds and (b) fails.
- **Refuted:** otherwise. Each part is reported separately.

### H4: fewer false alarms on requested instructions

**Hypothesis.** At matched TPR, ICT has a lower FPR on legitimate (request-aligned) instructions than every content-only detector.

**Protocol.**
1. Each detector's threshold is set on the evaluated set so that its TPR on the injected rows of V3-test equals 0.80.
   This is an oracle operating point, used only as a matching device.
2. FPR is then measured on the **aligned-instruction set**: the aligned members of the held-out V3-test pairs and of the agent pairs.
3. Supported if the paired-bootstrap CI of (detector FPR − ICT FPR) excludes 0 for every content-only detector.
4. A detector that cannot reach TPR 0.80 is reported as `n/a (max TPR=…)` and does not count against H4.

**Secondary analyses.** Matched TPR 0.50, and the request-aware comparators.

## 4. Decision table

**Prerequisites** (checked before any hypothesis is decided; each failure is reported):
- **P1.** V3 passes its content-free gates (v3_design §8, Decisions R2) on all split seeds.
- **P2.** Pairs pass validation:
  - Two independent human annotators label every held-out pair member (aligned / subverting / unclear).
  - Cohen's κ ≥ 0.6 on the label.
  - Only pairs on which both annotators agree with the intended labels are used.
  - **≥ 200 agreed pairs per held-out pair set** (V3-derived and agent-derived; A5, counted strictly as in A18):
    pairs in quads whose every member both annotators label with the intended label. Adjudicated pairs are a
    secondary robustness analysis.
    - The generator over-generates about 300 pairs per eval set. Two annotators from the project group label them
      independently; disagreements are adjudicated (A9).
    - At p = 0.5, n = 200 gives a binomial 95% half-width of about ±0.07, against ±0.10 for n = 100.
    - The cluster bootstrap is wider when one source doc or task contributes several pairs.
- **P3.** Pairs pass two leakage checks (amendment A4):
  - **(i) Request-only gate:** a TF-IDF+LR and a DeBERTa trained on the **user request alone** (train pairs) have
    held-out pair accuracy ≤ 0.60, run-mean point estimate. Otherwise the request phrasing gives the label away and
    the pairs carry an artifact, like C1.
  - **(ii) Content-identity check:** a content-only model (TF-IDF+LR on the context alone) trained on the train pairs
    scores held-out pair accuracy **exactly 0.5**, and so does each content-only public detector.
    - Any deviation means a pair's contexts differ. It is a build bug, fixed before any hypothesis is decided.
- **P4.** The C1 leakage claim is re-established with committed code.

## 7. Build order (amendment A8)

Each step starts only after the previous one is done. The calibration pool is on the critical path for H1 and H3b.

1. **V3 freeze.** Gates pass on split seeds 0–4, integrity checks pass, the benign pool is human-reviewed, then tag `v3-frozen`.
2. **Transfer harness**, including a reproduction of Liu 2026. AD-Matched, AD-Shift and TB-Matched are rebuilt
   with Liu's pinned scripts, and the reproduction is checked against Liu's released scores.
3. **Agent-style data and the calibration pool** (A3).
4. **V3 baselines.** H1 is decided here: V2- vs V3-trained DeBERTa on the agent sets, with calibration-pool thresholds.
5. **Pairs.** Generation, two-annotator labelling, adjudication, and the P2/P3 checks.
   - **Pair generation** (not annotation) may start in parallel with step 2, since it does not depend on ICT (A14).
     Annotation and adjudication follow the order above.
6. **ICT**, its ablations, and the H3a comparators. Comparator (c) is scored in the order fixed in
   `configs/frontier_detector.yaml` (A7).

The GPT-4.1 snapshot in A7 shuts down on 2027-01-14. **Comparator (c) must be fully scored by 2026-12-31** (A11). In this order it
needs the calibration pool (step 3) and the adjudicated pairs (step 5).
