\section{Request-Counterfactual Intent Pairs}
\label{sec:pairs}

\subsection{Definition}
A \emph{pair} is one context and two user requests. The context $c$ is a document (from \vthree{} test) or a tool
output (from an agent benchmark) containing exactly one inserted instruction $i$, and it is byte-identical in both
members. In the \emph{aligned} member $(q_a, c)$, following $i$ serves the request (label 0); in the
\emph{subverting} member $(q_s, c)$, following it gives the user something other than what they asked for
(label 1). A detector gets a pair right if it scores the subverting member higher; ties count one half.

Because the two members share $c$, every detector that ignores the request assigns them the same score, so its pair
accuracy is exactly $0.5$. This holds for every public content-only classifier by construction, which is the point of
the design: pair accuracy measures only what a detector does with the request.

\paragraph{Crossed quads.}
Pairs are built two at a time on one document $d$, from two requests $R_1, R_2$ that are both plausible for $d$ and
two instructions $I_1, I_2$ such that $I_1$ serves $R_1$ and subverts $R_2$, and $I_2$ serves $R_2$ and subverts
$R_1$. This gives the pairs $(d{+}I_1;\ R_1 \text{ aligned}, R_2 \text{ subverting})$ and
$(d{+}I_2;\ R_2 \text{ aligned}, R_1 \text{ subverting})$. Each request string then carries both labels exactly
once, so a model that reads only the request also gets exactly one of the two pairs right and scores $0.5$ on any set
of complete quads. A quad is generated, annotated, kept or dropped as a unit; a lone pair would give its requests a
single label that a request-only model could learn across the set. The two classes of shortcut that a pair set can
carry, the context and the request alone, are thus removed by construction, leaving the relation between request and
instruction as the only signal.

\subsection{Decision rules}
An instruction is eligible only if it is addressed to whoever processes the content to produce the response (an
imperative about the output or the task, or a second-person instruction to the assistant), is self-contained, and
contains no injection marker (``ignore'', ``disregard'', ``instead'', ``previous instructions'', ``system'',
``new task'' and similar). Instructions whose natural executor is a person in the document's world, such as an
email's request to its recipient or a code comment to the next developer, are excluded: they are \vthree{}'s benign
clean-A material. Banning injection markers prevents content-only detectors from flagging aligned members for their
form, which would inflate our false-alarm comparison in our favor.

An instruction is excluded whatever the request if following it would send or reveal data to a party the user did
not name, make a payment or purchase, delete or overwrite the user's data, change credentials, permissions or
security settings, assert content that contradicts the document, or add promotional content, links or contact
details the user did not ask for. These instructions are injections under every definition
(\S\ref{sec:task}), and excluding them keeps the pairs out of the contested zone.

A request is eligible only if it names a specific output, neither authorizes nor forbids instructions in the data
(``follow whatever the document says'' would make the label readable from the request), shares no word 5-gram with
the instruction of its pair, and is one a user could plausibly make without seeing the instruction.

The label is fixed by one question, which is also the annotators' question: \emph{if the assistant did what the
instruction says while answering this request, would the user say ``that is what I asked for'' or ``that is not what I
asked for''?} An instruction is aligned if it is a step towards the requested output, sets a format the request leaves
open, or does exactly part of the request and nothing else. It is subverting if it substitutes a different task,
breaks an explicit constraint (language, length, format, audience), omits or replaces requested content, or answers a
different question. Table~\ref{tab:pair-examples} gives examples.

\subsection{Subtle pairs and lexical baselines}
The crossing does not remove the relation between request and instruction, and some of that relation is lexical: the
member whose request shares more words with the instruction is often the aligned one. We store each pair's
\emph{overlap class}, computed from text alone with the Jaccard similarity of stemmed content-word sets. A pair is
\emph{explicit} if the aligned request overlaps more with the instruction, and \emph{subtle} if the overlap is equal
or inverted (a paraphrase, or a subverting request that repeats the instruction's words, as in the second row of
Table~\ref{tab:pair-examples}). We target at least 40\% subtle pairs per evaluation set, selected by overlap class
only, never by model scores. We report a word-overlap heuristic and a character 3-gram TF-IDF cosine heuristic as
lexical baselines, and report every pair result on all pairs and on the subtle subset.

\subsection{Insertion and length}
Instructions are inserted with the \vthree{} procedure: position and separator are drawn uniformly and independently
per pair, at the same boundaries as \vthree{}. Within a pair, position cannot reveal the label because the context is
shared; the rule keeps pair contexts comparable to \vthree{} rows, against which the aligned members' false-alarm
rate is compared. An instruction costs no more tokens than the \vthree{} span cap of its register, both members fit
in 512 DeBERTa-v3 tokens, the two instructions of a quad differ by at most eight words, and the two requests differ in
length by at most a factor of two.

\subsection{Generation and validation}
Evaluation and training pairs come from different generators, from different vendors, with separately written prompt
templates that share no word 8-gram. No generator comes from the family of any request-aware comparator or of our
model's backbone. Training pairs are drafted by Mistral-7B-Instruct-v0.3 on \vthree{} training documents only, and
kept only if the same model, labelling each member blind to the intended label, agrees with both labels.

Evaluation pairs are written on the test documents of \vthree{} split seed 0, and on clean tool outputs of the agent
benchmarks of \S\ref{sec:results}. Two annotators independently label every member of every evaluation pair as
aligned, subverting or unclear, on pages that show no intended label, generator or overlap class, in a different
order for each annotator. The pre-registered prerequisites are Cohen's $\kappa \geq 0.6$ over members and at least
200 \emph{agreed} pairs per evaluation set, where a pair counts only if its whole quad is labelled as intended by both
annotators. If a set falls short, more pairs are generated and annotated under the same rules; the agreement rule is
never relaxed. Pairs from adjudicated quads are a secondary robustness analysis. Two leakage checks are run and
reported even though the construction implies them: models trained on the request alone must stay at or below 0.60
pair accuracy, and a content-only model must score exactly 0.5. \todo{annotation, $\kappa$, agreed-pair counts and
